End-to-end testing

View .mdEdit on GitHub

swift test runs about 3,400 tests against fakes (FakeTart, FakeSSH, FakeGitea, ...) in about a minute and a half with --parallel (warm build) and no VMs and no network. That keeps the suite fast, but it can only prove kinhin agrees with its own model of a forge or a runner. The end-to-end (e2e) suite in Tests/E2E checks the model against the real thing: a real forge in a container, a real kinhin daemon, a real runner image, and a job that really runs inside a guest.

← Back to README · Contributing · Adding a forge

How it is built#

  • A separate Swift package (Tests/E2E/Package.swift). The root swift test and scripts/check.sh can never load it, so nothing here boots a container unless you run scripts/e2e.sh.
  • Swift Testing, not XCTest: parameterized @Test(arguments:) gives the forge × runtime matrix for free, tags group the tiers, and one .serialized parent suite (Infra) keeps the heavy suites from fighting over the Mac.
  • A black box. The suite drives the real kinhin binary as a subprocess and judges outcomes by what the forge itself reports, never by kinhin's own view of events. It has no dependency on KinhinKit.
  • Sandboxed. Every scenario gets its own support directory (KINHIN_SUPPORT_DIR=/tmp/ke2e-<id>: config, state, logs, daemon socket) and reads its forge tokens from the environment (KINHIN_TOKEN_STORE=env, a debug-build feature). It never touches your real config, daemon or Keychain. This is why scripts/e2e.sh builds a debug kinhin.

Running it#

Run it in CI. The script refuses to run outside CI unless KINHIN_E2E_LOCAL=1 is set, and that is for a local test the user asks for, never routine. Start the e2e.yml workflow by hand (workflow_dispatch, choosing the tier) and read its logs. The commands below are what the workflow runs, for reference; do not type them locally.

scripts/e2e.sh                # quick: CLI, security and coverage guards. Seconds, no Docker.
scripts/e2e.sh --local        # + real Gitea/Forgejo lifecycle, fleet behavior, smoke toolchains (Docker, container)
scripts/e2e.sh --full         # + GitLab CE and the whole toolchain catalog (hours, several GB)
scripts/e2e.sh --local -- --filter LifecycleTests     # anything after -- goes to `swift test`

--full turns the Tart macOS (macos-tahoe-base), Tart Linux (ubuntu) and host lanes on unless their variables are already set. Narrow the matrix with environment variables:

VariableEffect
KINHIN_E2E_FORGES=gitea,forgejoOnly these forges (gitea, forgejo, gitlab, github, buildkite, bitbucket, azuredevops)
KINHIN_E2E_RUNTIMES=docker,appleContainerOnly these runtimes
KINHIN_E2E_HEAVY=1Include GitLab CE (several GB, minutes to boot)
KINHIN_E2E_TOOLCHAINS=fullThe whole toolchain catalog instead of the smoke set
KINHIN_E2E_TART_BASE=<macOS tart image>Turn on the Tart macOS lane (bakes from it with image prepare --source)
KINHIN_E2E_TART_LINUX_BASE=<Linux tart image>Turn on the Tart Linux lane (e.g. ghcr.io/cirruslabs/ubuntu:latest)
KINHIN_E2E_HOST=1Turn on the host lane (jobs run on this Mac, in the sandbox's work dirs)
KINHIN_E2E_GITHUB_TOKEN, KINHIN_E2E_GITHUB_REPOTurn on the GitHub lane against a throwaway repository
KINHIN_E2E_BUILDKITE_TOKEN, KINHIN_E2E_BUILDKITE_SCOPETurn on the Buildkite lane against a throwaway organization; the scope is org/cluster and the cluster needs a kinhin queue (KINHIN_E2E_BUILDKITE_REPO overrides the placeholder repository the pipeline names)
KINHIN_E2E_BITBUCKET_TOKEN, KINHIN_E2E_BITBUCKET_SCOPETurn on the Bitbucket lane against a throwaway repository with one commit; the scope is workspace/repo, the token a repository access token with repository:write, pipeline, pipeline:write and runner:write
KINHIN_E2E_AZURE_TOKEN, _ORG, _PROJECT, _POOLTurn on the Azure DevOps lane against a throwaway project and its self-hosted pool (authorized for all pipelines); the PAT needs Agent Pools, Build and Code scopes. KINHIN_E2E_AZURE_REPO names another repository for the pipeline files, KINHIN_E2E_AZURE_FLOOR=1 runs with min_runners: 1 if the pool fails jobs fast when no agent matches
KINHIN_E2E_KEEP=1Keep the sandbox directories (config, logs) of a failed run
KINHIN_E2E_VIDEO_IMAGE=<image>Turn on the real-video test of kinhin video (a built video image, e.g. kinhin-video:local); KINHIN_E2E_VIDEO_RUNTIME=container|docker picks the runtime
KINHIN_E2E_GITEA_IMAGE, _FORGEJO_IMAGE, _GITLAB_IMAGEOverride the pinned forge images
KINHIN_E2E_AI=1Turn on the live healing-advisor lane (macOS 26+ with Apple Intelligence turned on)

A run that is killed (a closed terminal, a pkill from another session, a sleeping Mac) can leave a daemon, forge containers and /tmp/ke2e-* sandboxes behind. scripts/e2e.sh sweeps those before it starts and again when it exits, and scripts/e2e-sweep.sh does the same on its own. It only touches things the suite created (sandboxes named ke2e-*, containers named ke2e-* or ke2ed-*, or built from a ke2e-* image, and daemons recorded in a sandbox's daemon.pid), and does nothing while another run is active.

What the machine needs#

  • Apple Silicon, with Docker (Docker Desktop, OrbStack or Colima), and/or the container CLI, and/or Tart. Lanes whose runtime is missing are skipped.
  • A real fleet can keep running for Docker, Apple container and host lanes. The suite's daemon mints and adopts only ke2ed-* instances (KINHIN_INSTANCE_PREFIX, a debug-build switch), so a fleet's kinhin-* containers are never touched. The fleet and the suite still share the Mac's CPU, memory and disk. kinhin sizes each daemon from host totals and does not see the other one, so before an e2e run raise the fleet's reserve (cpu, memory) by the suite's share, and lower it afterward.
  • Tart lanes run beside a fleet too, up to Apple's cap. Apple caps running macOS VMs at two per Mac. A Tart macOS lane therefore refuses to start only while the fleet already runs two macOS VMs, since its own VM would be a third. A fleet's stopped VMs and its Linux VMs never block a lane. Leftovers of an earlier run (ke2ed-*) always block, and scripts/e2e-sweep.sh removes them. The rule is Instances.tartBlockers (Tests/E2E/Sources/E2ESupport/Runtimes.swift).
  • Plenty of free disk (the Docker VM filled up once during this work and silently broke pulls and container starts). Forge images, runner images and the Docker VM's own disk add up; a full Docker VM makes pulls fail with no space left on device.
  • A LAN address. Containers cannot reach the host's localhost, so the suite addresses its forges by the Mac's address (plain http, with allow_insecure_http: true in the sandbox config).
  • It cannot run in kinhin-xcode CI: that runner is itself a Tart VM, and Apple Silicon does not nest VMs. See .github/workflows/e2e.yml: run by hand (workflow_dispatch) on a dedicated Mac labelled kinhin-e2e, never on pull requests. The nightly and weekly schedules are switched on once that Mac exists (beta-2); until then the T2 and T3 cadences below are the target. Until that Mac is registered the workflow has no runner and the tiers cannot run at all: do not run them locally instead.

What is checked#

LifecycleTests (forge × runtime, from LifecycleCase.all: every ForgeKind × every RuntimeKind). A job is pushed to a real forge. The test then asserts, with the forge as judge:

  1. The job ran inside the guest: it opens a "proof" issue whose body is the guest's uname -s, hostname and working directory, and the kernel matches the runtime (Linux for containers and Tart Linux, Darwin for Tart macOS) and the hostname is not this Mac's. In host mode, where it is this Mac, the job must have run in its instance's work directory inside the sandbox.
  2. The instance that ran it is deleted afterwards, within the forge's exit rule (deregistration or idle grace).
  3. The forge no longer lists the runner (kinhin deregistered what it spawned).
  4. The access token is absent from kinhin's log and the daemon is still alive.
  5. A job that fails is reported failed by the forge, produced no proof, and a good job afterwards still runs.

FleetBehaviorTests: pause/resume (a paused fleet starts nothing, even after a runner is killed), a SIGKILLed daemon whose orphan runner is reconciled away by the next daemon, the max_runners ceiling with two concurrent jobs, a job longer than the idle grace on every Gitea/Forgejo lane, a picked-up job not being scaled down under it with no floor (Gitea 1.26, Forgejo, GitLab), a forge that hangs mid-job (docker pause for 45 s) costing neither the runner nor the job, the Tart warm_pool (a warm VM waits, the next job claims it), and a broken image backing the fleet off instead of crashing. It also pins a known limitation (below) with withKnownIssue, which fails loudly the day the limitation is fixed.

FeatureTests: on a busy fleet, status --json shows the busy instance, pipeline --json lists it, logs shows the daemon's history with no token, and requeue/skip are refused clearly on a forge without a queue API. Routing precedence with two pools (Docker default, Apple container by repo route): a repo route beats the default on Gitea and Forgejo; the workflow route is pinned as a known issue.

VideoTests (quick tier, hermetic): kinhin video init | list | build | music search | add | list through the real binary against a local stand-in for the music library (MusicLibraryStub, a small Python server; a debug kinhin is pointed at it with KINHIN_OPENVERSE_URL, which release builds never read). It checks that search honors the license and length filters and lists built-in tracks first; that add downloads the file with the right SHA-256, writes the provenance .json, and sets music: in the video's YAML while keeping its comments; that a non-reusable license is refused (exit 2) before anything is saved and CC BY needs --license cc-by and brings its credit; that several videos need --video and only that one is edited; that a JSON config is not rewritten; that theme new writes a starter that extends a built-in theme and the video suite accepts it; and that a rate-limited or unreachable library is exit 4 with the built-in tracks still shown. One test builds a real video in a container from a track added with music add and checks music.json and the finished mix's loudness; it runs when KINHIN_E2E_VIDEO_IMAGE is set (it is skipped otherwise).

HealingTests (Gitea on Docker; the healing agent on second-scale cadences with KINHIN_HEALING_TIMINGS=fast, a debug-build switch): a reserve no Mac can meet makes the agent prune a planted stale cache entry on its own, then queue an image prune for approval; heal exits 1 and status carries the healing alert until heal dismiss closes it, and a dismissed fix is not raised again. healing.auto: none turns the cache prune into an approval that heal approve runs; healing.enabled: false journals nothing while jobs still run. A broken image (runners failing on a healthy runtime, which no rule covers) is surfaced with no advisor; with a fixed advisor (KINHIN_HEALING_ADVISOR=stub:…, debug only) a pick outside the allowlist is ignored and a destructive pick only waits for approval. On the Tart Linux lane a warm VM deleted out of band is recycled on its own and the next job still runs. With KINHIN_E2E_AI=1 the real on-device model answers from the daemon with an allowed fix or none. Every scenario checks that the daemon survived, the token never reached the log and the journal is owner-only. HealingCLITests (quick tier): heal with no daemon (exit 1, a stable document), approve/dismiss argument and daemon errors, healing: validation (exit 3) and export, and the MCP heal_status tool with no approving tool beside it.

TelemetryTests (quick tier, no Docker; a real kinhin daemon with an unreachable forge, OTLP to a local stand-in collector, OTLPCollectorStub, a small Python server that records each POST's path, headers and the printable strings in its body, so a test can tell which metrics, span names and resource attributes an export carries without a protobuf decoder). It checks, against the daemon as a black box:

  • Prometheus: GET /metrics answers with the always-published kinhin_ gauges and the forge request counter (by forge and status class, never by URL); only GET /metrics is served; a bare prometheus_listen port is unreachable on the LAN address while 0.0.0.0 is reachable and logs a warning; a port that is already taken leaves telemetry off and the daemon up.
  • Reload: kinhin config reload leaves an unchanged listener alone, moves it to a new port (same daemon process, old port released), closes it when enabled: false, re-opens it, and refuses an invalid config (exit 3) before it reaches the daemon.
  • OTLP: metrics and logs reach the collector with the kinhin resource (service.name, service.version, host attributes, the user's attribute, the SDK's own) and keep coming; collector headers from OTEL_EXPORTER_OTLP_HEADERS arrive as request headers and never in the log or the exported data; protocol: grpc opens an HTTP/2 connection (HTTP2PrefaceProbe); an unreachable collector never hurts the daemon; a stopping daemon flushes what it had not yet exported (export_interval_seconds: 3600).
  • Environment: OTEL_EXPORTER_OTLP_ENDPOINT beats the config endpoint, OTEL_METRICS_EXPORTER=none removes a signal, OTEL_RESOURCE_ATTRIBUTES adds attributes but service.name cannot be replaced, OTEL_SDK_DISABLED=true wins over enabled: true. The sandbox strips inherited OTEL_* variables so a developer's collector never leaks into a run.
  • Off by default: with no telemetry: section, or enabled: false naming a port and a collector, nothing is bound and the collector receives nothing.
  • Logs and validation: log_format: json writes one JSON object per line (even with telemetry off) and the default stays plain text; thirteen bad telemetry: values are each exit 3 and name their key, and a config using every key validates.

AlertsTests (quick tier, no Docker; a real kinhin daemon with an unreachable forge, alerts to a local stand-in webhook, WebhookStub, a small Python server that records each POST's path, headers and body). It checks: a fleet that cannot start sends one startup alert in each of the generic, Slack, Discord and ntfy shapes (and never the forge token); with no alerts: section or enabled: false nothing is sent; a webhook answering 500 is tried and the daemon keeps answering status; kinhin alerts test posts once, exits 4 on a refusing endpoint and 3 with no webhook; two webhooks: with different events: each receive only their own event types (the startup alert reaches the one that selected it) and alerts test --webhook NAME reaches only that one, and the legacy single webhook: still works; a plain-http, non-loopback URL is refused (exit 3). A problem that is raised and then clears needs a fleet that starts, so that pair is covered by the unit suite; a real Slack, Discord or ntfy endpoint is a manual check.

TelemetryLifecycleTests (local tier: a real forge and runtime, per forge × runtime cell, the daemon exporting to the stub and to /metrics): after a real job, kinhin_jobs_picked_up and kinhin_jobs_completed count it, each of clone, boot, register and teardown was timed, cicd_pipeline_run_duration is a histogram and cicd_pipeline_result is the forge's verdict (success on every forge but Bitbucket, which cannot say and reads unknown), and one job trace reaches the collector with the kinhin.job root and its phase spans, the instance id as a span attribute, and the kinhin resource; the instance's log lines arrive with its id. No instance name, job name or token appears on any metric, and no token on any export. A failing workflow is still counted as picked up and completed (failure on every forge but Bitbucket, unknown there, never success), is not a cicd_system_errors sample, and the next job is counted too.

CLITests: version and exit codes (usage 2, config 3), --json errors, config init on a pristine machine, config migrate, config export and import, the account lifecycle, doctor (and a support bundle with no token in it), runtimes and routes, read-only inventory commands, toolchain detection, workflow test and workflow route, reset, and an MCP handshake over stdio.

SecurityTests (from security.md): support directory, config, log directory, log file and daemon socket are owner-only; plain http to a remote forge is refused unless opted in (loopback is allowed); a host route needs --consent; tokens never appear in command output or the log.

ToolchainTests: kinhin bench toolchains --thorough cold-installs, verifies and runs a workload for tools in a real guest on Docker, Apple container and Tart Linux (a smoke set by default, every one of which must actually run; the whole catalog with KINHIN_E2E_TOOLCHAINS=full), failing on any failed row or any skip without a reason; and a real runner job on every guest runtime that runs kinhin-toolchain install node@22 and proves it.

CoverageTests keep the suite honest as kinhin grows. They need no infrastructure:

  • every forge in kinhin auth set --help must be classified in CoverageTests.forges as live, gated or waived with a reason, so adding a forge fails here until someone decides how it is tested;
  • every runtime kinhin runtimes route add accepts must have a RuntimeKind (Tart twice: macOS and Linux guests), so a new runtime joins the forge × runtime matrix or fails here;
  • every command in kinhin help must map to a test or a stated reason in CoverageTests.commands, and no entry may name a command that no longer exists;
  • every command must answer --help with exit 0.

Hosted forges#

GitHub, Buildkite, Azure DevOps and Bitbucket are real services, so their lanes are gated on credentials. The full set-up (accounts, tokens, secrets, what the first run must confirm) is in Setting up the hosted e2e lanes.

Adding a forge#

Follow adding-a-forge.md, then:

  1. Add a ForgeFixture in Tests/E2E/Sources/E2ESupport/ (see GiteaFixture): start a throwaway server, mint a token, create a repository, push workflows, and report the proof issue, run statuses and registered runners from the forge's own API.
  2. Add a case to ForgeKind and to the switch in Lane.start.
  3. Classify it in CoverageTests.forges. If it cannot run locally, mark it gated or waived and say why.

Known limitations#

  • Gitea 1.24 and older show no queued job until a runner exists. The task API lists a task only after a runner asks for it, so with min_runners: 0 kinhin never sees the work. The suite runs those versions with min_runners: 1 (a warm runner) and pins the blind spot in FleetBehaviorTests.queuedJobIsSeenWithoutAFloor, which expects it as a known issue on Gitea 1.24.
  • A min_runners floor lands in the default pool. Host lanes therefore run without one (Gitea 1.26, Forgejo, GitLab), since a host route can never be the default.
  • Workflow routes never match on Gitea or Forgejo. Neither queue endpoint names a job's workflow (a Gitea 1.26 job carries only its name, labels, branch, commit and URLs; the run carries the workflow file, not its name:), so an owner/repo@Workflow route is ignored and the repo route or labels decide. Pinned in FeatureTests.routesWinInPrecedenceOrder. Repo routes work.
  • Gitea 1.25+ and Forgejo 11+ do not have that limit. kinhin reads /actions/jobs?status=queued (Gitea; a job nobody has picked up is queued, and waiting matches nothing) and /actions/runners/jobs?labels= (Forgejo; the labels are the runner's label set). Verified live with no floor on Gitea 1.26.4 and Forgejo 11. Gitea 1.25.5 listed the same job on the same endpoint; the no-floor lifecycle has not been run on 1.25 itself.
