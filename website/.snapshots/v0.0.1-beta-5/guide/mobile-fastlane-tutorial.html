GUIDE / MOBILE RELEASES

Tutorial: your first TestFlight or Play internal build

View .mdEdit on GitHub

This walks through a first release from a clean start: scaffold the project, set up the credentials once, run a beta lane by hand, then run it from CI. It takes about an hour the first time, most of it waiting on Apple and Google.

← Back to mobile releases · Credentials · Troubleshooting

What you need#

  • A Mac with kinhin installed (kinhin on your PATH), Xcode, and Ruby 3.2 or newer. The macOS system Ruby (2.6) is too old. Install Ruby 3.3 with Homebrew (brew install ruby@3.3) or rbenv.
  • For iOS: an Apple Developer Program membership. The Account Holder requests API access, and an Account Holder or Admin creates the team key.
  • For Android: a Google Play Console developer account, and a Google Cloud project you can create a service account in.
  • A repository for the app on any supported forge (GitHub, Gitea, Forgejo, GitLab, Bitbucket, Azure DevOps or Buildkite), with a runner that has the kinhin-xcode label.

Your app already builds locally. Check that first: flutter build, npx react-native run-ios, or Xcode and Android Studio for native apps.

1. Scaffold the project#

From anywhere, point kinhin mobile init at the project folder:

kinhin mobile init --dry-run ~/code/my-app   # see what would be written
kinhin mobile init ~/code/my-app

It detects the framework. Flutter and React Native get fastlane in ios/ and android/; a native app gets it at its root; an Expo app gets eas.json only, unless you run npx expo prebuild first (see the reference). It writes a Gemfile that pins fastlane, the lanes, and a release pipeline for your CI system. kinhin picks the system from your origin remote, or from --ci github|gitea|forgejo|gitlab|bitbucket|azure|buildkite:

Your forgePipeline fileRunner
GitHub.github/workflows/mobile-release.ymlruns-on: [self-hosted, kinhin-xcode]
Gitea, Forgejo.gitea/workflows/mobile-release.yml, .forgejo/workflows/mobile-release.ymlruns-on: [kinhin-xcode]
GitLab.gitlab/mobile-release.yml, included from .gitlab-ci.ymltags: [kinhin-xcode]
Bitbucketbitbucket-pipelines.yml (custom pipeline)runs-on: [self.hosted, macos, kinhin-xcode]
Azure DevOps.azure-pipelines/mobile-release.ymlpool kinhin
Buildkite.buildkite/mobile-release.ymlqueue kinhin

Every non-GitHub system also gets .kinhin/mobile-release.sh, which holds the release steps. Existing files are kept, so you can run it again safely. The reference has the details.

Install the gems and list the lanes, from the folder that holds fastlane/:

cd ~/code/my-app/ios        # Flutter and React Native; a native app stays at its root
bundle install
bundle exec fastlane lanes

You should see ios beta and ios release (and android beta and android build in the Android folder). Commit the scaffolded files before going on.

2. Create the App Store Connect API key (iOS)#

App Store Connect uses an API key instead of your Apple ID password. In App Store Connect, open Users and Access, then Integrations, then App Store Connect API, and request access if you have not yet (only the Account Holder can). Create a Team key, and download the .p8 file. Apple's page says API keys "can only be downloaded once". Apple's page does not list which roles can upload builds, so confirm the key works with a first upload.

Note the Key ID and the Issuer ID. You will store the .p8 contents as a secret in step 4. The details are in credentials.

3. Set up code signing with match (iOS)#

match keeps your signing certificates and profiles in a private, encrypted git repository, so CI can use them without you copying certificates by hand.

  1. Create an empty private repository for certificates on any git host, for example my-org/certificates.
  2. Choose a passphrase for it and keep it safe. It becomes MATCH_PASSWORD.
  3. Run match once from your own Mac, not on CI, to create the certificates and profiles:
cd ~/code/my-app/ios
MATCH_GIT_URL=git@git.example.com:my-org/certificates.git MATCH_PASSWORD='your passphrase' \
  APP_IDENTIFIER=com.example.myapp APPLE_TEAM_ID=ABCDE12345 \
  MATCH_READONLY=false bundle exec fastlane match appstore

match asks for the passphrase, unless MATCH_PASSWORD is set, which avoids the prompt. Afterwards the repository holds the encrypted certificates. CI runs match readonly, so it never creates or changes them.

4. Add the secrets#

Add the secrets listed in the header of the pipeline file kinhin wrote. Where you add them depends on the forge:

ForgeWhere
GitHubSettings > Secrets and variables > Actions
Gitea, ForgejoRepository Settings > Actions > Secrets
GitLabSettings > CI/CD > Variables (mask them; protect them for protected branches)
BitbucketRepository settings > Pipelines > Repository variables (secured)
Azure DevOpsPipelines > the pipeline > Variables (keep this value secret)
Buildkitethe agent environment or a secrets manager; Buildkite has no secret store of its own

For iOS you need ASC_KEY_ID, ASC_ISSUER_ID, ASC_KEY_P8, MATCH_GIT_URL, MATCH_PASSWORD, APPLE_TEAM_ID, APP_IDENTIFIER and IOS_SCHEME. Each one is explained in credentials.

IOS_SCHEME is the Xcode scheme to build. For Flutter it is Runner, which is the default when the secret is empty.

5. Set up Android (optional, same steps)#

  1. Create an upload keystore once, and keep the file and its passwords somewhere safe:
keytool -genkeypair -v -keystore upload.keystore -alias upload -keyalg RSA -keysize 2048 -validity 10000
  1. Store it base64-encoded, as ANDROID_KEYSTORE_BASE64. On macOS: base64 -i upload.keystore | pbcopy.
  2. Create a Google Cloud service account, enable the Google Play Developer API for it, and invite it in Play Console with Release apps to testing tracks permission for your app. Store its JSON key as PLAY_SERVICE_ACCOUNT_JSON.

The full steps are in credentials.

The app must exist in Play Console before the first upload. Create it there, with the package name you put in ANDROID_PACKAGE_NAME. The first upload is made by hand in Play Console, as the fastlane supply docs say. The lanes can upload after that.

6. Run a beta locally first#

Before CI, run the lanes on your Mac. The lanes read the same variables as CI, but the API key and the keystore are files, so point to them rather than pasting their contents. Keep the secret values out of shell history by putting them in a file you do not commit, such as ~/.config/my-app/release.env, and loading it with set -a; source for the session:

cd ~/code/my-app/ios
export ASC_KEY_ID=... ASC_ISSUER_ID=... APP_IDENTIFIER=com.example.myapp APPLE_TEAM_ID=ABCDE12345
export ASC_KEY_FILEPATH=~/keys/AuthKey_XXXX.p8     # the .p8 file, not its contents
export MATCH_GIT_URL=git@git.example.com:my-org/certificates.git MATCH_PASSWORD=...
bundle exec fastlane beta

For Android, set PLAY_SERVICE_ACCOUNT_JSON to the JSON file's contents (for example $(cat ~/keys/play.json)), and set ANDROID_KEYSTORE_PATH to the keystore file with its passwords and alias. CI does the same through the workflow.

A successful run uploads the build to TestFlight. Apple then processes it for a few minutes before it appears there. Android works the same way, from the android folder: bundle exec fastlane android beta uploads to the internal track. If you only want to check that the Android bundle builds and is signed, run bundle exec fastlane android build, which does not upload.

7. Run it from CI#

Start the mobile-release pipeline by hand and pick beta for the lane:

ForgeHow
GitHub, Gitea, ForgejoActions > mobile-release > Run workflow
GitLabBuild > Pipelines > Run pipeline, with MOBILE_LANE set to beta
BitbucketPipelines > Run pipeline > custom: mobile-release
Azure DevOpsrun the pipeline made from .azure-pipelines/mobile-release.yml
Buildkitebuild a pipeline whose steps upload .buildkite/mobile-release.yml

On GitHub the job installs Ruby, and for Flutter and React Native the framework tools first, then runs the lane. On the other systems .kinhin/mobile-release.sh does this, using the toolchains on your runner image. If it fails, the first error is in the log of the failing step. The troubleshooting page lists the failures we have seen, with what to do about each.

Use release only after a beta build has finished processing and you have checked it in TestFlight. The release lane uploads the build to App Store Connect without submitting it for review.

Where to go next#

  • The reference covers each framework, the monorepo layout and the Expo route.
  • Add a second lane for production, or wire the release lane to a tag, once beta is working for you.
